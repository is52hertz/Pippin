## 2. Decisions that supersede parts of the parent prd

### 2.1 Shortcuts: elevated from "case-by-case patch" to a batch-two module

User decision. This does **not** reopen Decided Position 4's routing-ladder
conclusion — Shortcuts is still not a routing tier and still not an
abstraction layer. What changed: it becomes a *user-curated module* in its own
right.

- **Curation model:** only shortcuts inside one designated folder in
  Shortcuts.app (working name: folder `AI`) are exposed. Putting a shortcut in
  the folder *is* the authorization act. Keeps the list short (token budget)
  and the accidental surface zero.
- **Tools:**
  - `pippin_shortcuts_list` — folder-scoped only.
  - `pippin_shortcuts_run` — official `shortcuts run` CLI; one text-or-file
    input slot, capture stdout/output file; wall-clock timeout like every
    other backend call.
  - `pippin_shortcut_create` — agent drafts the workflow plist →
    `shortcuts sign` (official CLI) → open the signed file → **the user
    confirms the import dialog in Shortcuts.app**. That human gate is the
    safety model. The plist action format is community-reverse-engineered:
    common actions generate reliably, complex/third-party actions degrade —
    the tool description must say so honestly.
- **Why it earns module status:** the capability surface is authored by the
  user's own hands (AI can trigger, never rewrite), and `shortcuts` CLI is the
  only official bridge to Focus modes, HomeKit, and the App-Intents-only app
  world that AppleScript cannot reach.
- **prd edits required:** soften Decided Position 4's "never a module"
  phrasing to "never a routing tier"; remove "Any `shortcuts run` patch" from
  Out of Scope (it moves to batch two).

### 2.2 Escape hatch priority may drop further

With the Shortcuts module covering part of the long tail through a safer
channel, `script_run`/`app_dictionary` moves to batch three. Design position
in `design.md` §14 is unchanged.

## 3. New module: Health — via the user's Exporter iOS app

Mac has no HealthKit; health data is permanently out of reach for a macOS
process. The user's own companion project closes the gap:

- **Exporter** (github.com/is52hertz/Exporter): native iOS 26 app, read-only
  HealthKit export into a versioned, LLM-friendly JSON ("schema v3": metrics
  grouped with hoisted `columns`/`unit`, rows as compact arrays, deduplicated
  `sources` index, ISO-8601, incremental mode via anchored queries with
  deferred anchor commit). Already supports POST to a configured endpoint with
  an `Authorization` bearer header.
- **Pippin's role:** ingest → local accumulating archive → query tools
  ("average resting HR last month", "total running distance this year").
- **Ingest, two stages:**
  1. *Batch two:* watch an agreed iCloud Drive folder that Exporter shares
     files into. Zero network pairing; C1 (loopback-only) untouched.
  2. *Batch four:* LAN POST endpoint (e.g. `/ingest/health`) once per-token
     permission tiers exist (§5). A non-2xx response must not advance
     Exporter's incremental anchor.
- **Push-only, decided:** "Mac pulls from iPhone via GET" is rejected — iOS
  will not keep a listener alive in background; pulls would routinely find
  nobody home.
- **Exporter-side work** is drafted in repo-root `exporter-issues-draft.md`
  (user's staging file while GitHub is down; destined for that repo's issues).
  Do not include it in task commits; do not delete it.

## 4. New module: Screen Time — batch two, schedule early

Empirical findings from tonight (2026-08-17/18), all performed read-only on a
file copy:

- **Source:** `~/Library/Application Support/Knowledge/knowledgeC.db`
  (SQLite / Core Data store).
- **Full Disk Access is a hard gate:** without it, even listing the directory
  fails with `Operation not permitted` (observed from the host process
  tonight). Direct evidence for C2/C3.
- **Verified content** (table `ZOBJECT`, filter `ZSTREAMNAME`):
  `/app/usage` = 8 302 rows, `/app/webUsage` = 911 rows. Observed window
  2026-07-21 → 2026-08-17 — the ~4-week rolling retention is real and older
  data is unrecoverable.
- **Format notes:** timestamps are Core Data epoch
  (`unix = value + 978307200`); a plain copy of `knowledgeC.db` +
  `-wal` + `-shm` together passes `PRAGMA integrity_check`.
- **Existing snapshot:** the user manually backed up tonight to
  `~/Documents/ScreenTime-Backups/2026-08-17/` (~62 MB, verified).
- **Module shape:** read-only parse + a daily job appending new events into
  Pippin's own archive (the only way to retain history beyond the rolling
  window — every day it isn't running is data lost, hence "schedule early")
  + query tools. Falls under `design.md` §4 SQLite discipline: probe at
  startup, degrade loudly, never silent-empty.

## 5. Remote access and per-token tiers — batch four, one batch-one allowance

- **Goal:** cloud agents (ChatGPT / Claude web custom connectors) reach Pippin
  through a tunnel (Cloudflare Tunnel, Tailscale Funnel, ngrok).
- **Key fact:** tunnel daemons connect to `127.0.0.1` locally, so C1's
  loopback-only bind never changes. Remote access is purely additive.
- **Requirements when built:** multiple bearer tokens with per-token
  permission tiers (a remote token sees read-only tools only — the
  prompt-injection blast radius of a web agent must not include destructive
  tools); an explicit default-off "remote access" switch in Settings; separate
  token minting/revocation.
- **Batch-one allowance (the only thing asked of the skeleton child now):**
  shape the token validation model so "N tokens, each mapped to a tier" is a
  natural extension. Implementing a single token is fine; just don't hardcode
  one-token-equals-full-access so deeply that tiers force a rework.

## 6. Official-interface inventory (A–D tiers)

Shared basis for the roadmap; only existed in the side session until now.
Tiering is by how official and how reliable the access channel is.

**Tier A — public frameworks (structured, TCC-gated, most reliable):**

| Domain | API | Notes |
|---|---|---|
| Calendar | EventKit | full CRUD |
| Reminders | EventKit | full CRUD (batch one) |
| Contacts | Contacts | full CRUD |
| Photos | PhotoKit | library/albums read, search by date/place, export |
| Maps | MapKit | POI search, geocoding, directions (service, not personal data) |
| File search | Spotlight / CoreSpotlight | also finds indexed mail |
| Clipboard | NSPasteboard | trivial, high agent utility |
| OCR | Vision | text from any image/screenshot |
| Screen capture | ScreenCaptureKit | screen-recording TCC |
| Local music library | iTunesLibrary | read-only |
| Translation | Translation (macOS 15+) | on-device |
| Weather | WeatherKit | **requires paid dev account → unavailable for this project (O2)** |

**Tier B — official AppleScript dictionaries (old but sanctioned; medium-high
reliability):** Mail (read/search/send/move/delete — search too slow, hence
the SQLite accelerator), Notes (read/create/edit; attachments weak), Messages
(**send only**), Safari (tabs, current page URL/content — content needs the
"Allow JavaScript from Apple Events" toggle), Finder, Music (playback
control), iWork trio (surprisingly good dictionaries), and third parties that
ship dictionaries (Chrome, Spotify, Things, OmniFocus, iTerm, …).

**Tier C — official CLIs (sanctioned but scattered):** `shortcuts`
(run/list/sign — the bridge to Focus, HomeKit, App-Intents apps),
`networksetup` (Wi-Fi), `pmset`, `say`, `defaults`, System Events appearance
(dark mode).

**Tier D — private databases only (Full Disk Access; assume breakable, per
design §4):** Screen Time (`knowledgeC.db`, verified tonight), Messages
history read (`chat.db` — the only read path), Safari history (`History.db`),
Mail Envelope Index (accelerator for Tier B Mail, batch one).

**Impossible / policy-excluded (record as permanent):** Health on-Mac (no
HealthKit on macOS — permanently via Exporter, §3), Keychain/passwords
(technically possible, excluded by policy), FaceTime / Podcasts / TV / Books
(no framework, no dictionary), full System Settings control (only the small
Tier-C subset above; UI-scripting the Settings app is rejected as too
fragile).

## 7. Consolidated roadmap

Batches two+ are route-level only — child tasks get created when work starts,
per Trellis. Ordering logic: batch two is official-channel, read-heavy
horizontal scaling; write expansion and the escape hatch concentrate in batch
three because they share batch one's safety primitives; everything that needs
token tiers lands together in batch four so the security mechanism is never
half-built.

**Batch 1 (planned, task-level):** skeleton/transport · Reminders CRUD ·
Mail read/search.

**Batch 2 (high value, low risk):**
- Calendar (EventKit; shares most of the Reminders module's code — cheapest)
- Contacts
- Shortcuts module (§2.1)
- Screen Time (§4 — early, every idle day loses data)
- Health, stage 1: iCloud-folder ingest + archive + query (§3)
- Clipboard + screenshot-OCR (NSPasteboard / ScreenCaptureKit / Vision)
- Spotlight file search

**Batch 3 (write expansion + escape hatch):**
- Mail writes (send/move/flag; same two-phase protocol)
- Notes; Messages send (send-only)
- Safari (tabs / current page), Finder, Music
- Small System-Settings module (official channels only: appearance, volume,
  Wi-Fi; Focus via the Shortcuts module)
- Generic escape hatch `script_run` + `app_dictionary` (design §14; own
  security review)

**Batch 4 (network + fragile backends; all gated on token tiers):**
- Token tiers + remote-access switch (§5)
- Health, stage 2: LAN POST ingest from Exporter
- Cloud-agent connectors via tunnel
- Tier-D long tail: Messages history read, Safari history (most fragile, last)

**Permanent non-goals:** Health read on-Mac; Keychain; FaceTime / Podcasts /
TV / Books; general System Settings control; notarization/distribution
(free-tier signing only, per O2).
